# Deploying / handing over miraex.com

Everything here was checked against the running site on 2026-08-15. Numbers in the
inventory are real counts, not estimates.

## 1. What the site is made of

| Part | Where it lives | Notes |
| --- | --- | --- |
| 13 pages + front page | database (`wp_posts` + `mfn-page-items` postmeta) | generated by the builders in `docs/build/`, see §6 |
| Header, footer, mega menu | database — `template` posts #3, #52, #78 | assigned via the `mfn_header_entire_site` / `mfn_footer_entire_site` options |
| 21 reusable sections | database — `template` posts #80–#100 | `mfn_template_type = 'section'`, see `docs/build/README.md` |
| Nav menu (10 items) | database — `nav_menu` term + items | the **Solutions** item carries `mfn_menu_item_megamenu = 78` |
| Contact form | `build/lib_hubspot.php` → HubSpot | posts to HubSpot's public submissions API; portal `9201667`, form `f1490e22-…`. No API key, nothing secret in the page |
| SEO metadata | database — `rank_math_*` postmeta + `rank_math_options_titles` | generated from `_miraex_meta_description` by `build/migrate_seo.php` |
| 23 media items + 14 client logos | `wp-content/uploads` + `wp_posts` | |
| Design layer + builders | `wp-content/themes/betheme-child` | 2.8 MB |
| Generated stylesheets | `wp-content/uploads/betheme/css/post-*.css` | derived; can be regenerated, see §4 |

Only **WordPress core** has to be installed separately; everything else is in the archive.

The **betheme** parent (v28.5.7) travels with it, but a purchase code is still needed to
receive theme *updates* — an out-of-date paid theme is one of the most common ways a
WordPress site is broken into, so this is worth sorting out rather than deferring.
- **Contact Form 7** — no longer used by any page; the contact form goes to HubSpot.
  Keep it only if the old CF7 submission history matters, otherwise deactivate it.
- **Rank Math SEO** — ships in the archive; `build/install_rankmath.php` can reinstall it
  and `build/migrate_seo.php` configures it
- **LiteSpeed Cache** — ships in the archive; `build/install_litespeed.php` reinstalls it
  and `build/configure_litespeed.php` applies the settings (§9)

## 2. Export

```bash
wp-content/themes/betheme-child/docs/build/export_site.sh [output-dir]
```

Reads the credentials out of `wp-config.php` and writes:

- `miraex-db-<stamp>.sql` — full database (~4.5 MB)
- `miraex-content-<stamp>.tar.gz` — the whole of `wp-content` the site needs (~28 MB):
  `themes/betheme`, `themes/betheme-child`, `plugins`, `uploads`. Untar it and WordPress
  has everything except its own core.

  Both the parent theme and the plugins ship deliberately. **betheme** is paid, but this
  is the same site moving to its own server under the same licence — without it nothing
  renders at all, so "install it separately" just hands the receiving side a blank page
  and a shopping trip. **Plugins**, because the database records Rank Math as active: if
  its files are missing, WordPress deactivates it during load and every SEO tag vanishes
  with no error anywhere.

  Keep the archive private. It carries a paid theme, and the database dump carries user
  emails and password hashes. Neither belongs in the git repository, which is why both
  folders are ignored there.
- `README-first.txt`

Run it where the database is reachable. On the current laradock setup that is the
workspace container:

```bash
docker exec laradock-workspace-1 bash \
  /var/www/.../wp-content/themes/betheme-child/docs/build/export_site.sh /tmp/miraex-handover
```

The parent theme is inside the archive; nothing has to be shipped alongside it.

## 3. Import

1. Install WordPress, drop in `betheme`, activate **Contact Form 7**.
2. Untar the content archive over `wp-content/`.
3. Import the SQL into an empty database.
4. Point `wp-config.php` at that database.
5. **Rewrite the URLs — do not use `sed`.** 17 rows of `mfn-page-items` hold
   PHP-serialized arrays whose strings are length-prefixed
   (`s:66:"https://miraex.com/wp-content/uploads/…"`). A plain text replace changes the
   string without changing the `66`, and BeBuilder then fails to unserialize the page —
   the page renders empty. Use a serialization-aware tool:

   ```bash
   wp search-replace 'https://miraex.com' 'https://new-domain' --all-tables --precise
   ```

   or the **Better Search Replace** plugin, or `interconnect/it` srdb. Any of the three
   is fine; a text editor and `sed` are not.
6. Activate the **betheme-child** theme (`stylesheet = betheme-child`,
   `template = betheme`).

## 4. After the import — checks that actually catch breakage

1. **Permalinks**: Settings → Permalinks → Save (structure is `/%category%/%postname%/`).
   Without this every inner page 404s.
2. **Clear the Rank Math sitemap cache.** It stores each sitemap as an XML file under
   `uploads/rank-math/` and serves it verbatim, so pages added later never appear —
   `build/migrate_seo.php` deletes them (its own invalidator goes through WP_Filesystem,
   which falls back to FTP on the CLI and fatals).
3. **Flush the rewrite rules** (the Permalinks save in step 1 does this). Rank Math takes
   over `/wp-sitemap.xml` and serves `/sitemap_index.xml` from rewrite rules — without a
   flush the site has *no* working sitemap at all.
4. **Regenerate the BeTheme CSS**: BeTheme → Options → *Regenerate CSS* (or re-run the
   builders, §6). `uploads/betheme/css/post-*.css` is derived data and is keyed by post
   ID — it survives an import unchanged, but regenerate anyway if IDs moved.
5. **Front page**: Settings → Reading must show the *Home* page (option `page_on_front`).
6. **Mega menu**: Appearance → Menus → Solutions must still show the mega menu template.
   This link is a single postmeta row (`mfn_menu_item_megamenu = 78`) that was set by
   hand — it is the one thing no script recreates.
7. **Contact form**: see §5.
8. Load `/`, `/technology/`, `/contact/` and check at 1440px and 390px.

## 5. The contact form

It posts straight to HubSpot from the browser — no plugin, no API key, no server round
trip. Config is at the top of `build/lib_hubspot.php`.

HubSpot **ignores field names that are not on the form, silently and with a 200 response**:
a wrong name loses that answer without any error anywhere. The names in use were confirmed
against the live form (an incomplete POST is rejected with `REQUIRED_FIELD` errors that
name every required field, and creates no contact):

| form field | HubSpot property |
| --- | --- |
| First name | `firstname` |
| Last name | `lastname` |
| Work email | `email` |
| Organisation | `company` (optional) |
| How can we help? | `miraex_intent` (custom; CRM values equal the labels) |
| Message | **`comments`** — not `message` |
| Consent | `consent`, sent as `"true"` |

If HubSpot's form changes, re-check with the same trick before trusting a green response.

Spam is handled by a honeypot field rather than a captcha: no third-party service, no
hosting dependency, nothing for a visitor to solve.

**A honeypot needs a meaningless name.** The first version called the hidden field
`website_url` and labelled it “Company website” — Chrome autofill and password managers
recognised that and filled it in for real visitors, whose messages were then dropped as
bot traffic. The form reported success and sent nothing; nothing appeared in HubSpot and
nothing appeared in any log. The field is now `mx_r9` with no meaningful label, and a
filled trap only counts as a bot when **no key press or pointer press ever happened on
the form** — automation produces neither, autofill does not clear that flag on its own.
If the trap is ever renamed to something a browser can interpret, this comes back.

## 6. Generated vs hand-made — read before re-running anything

Page and template content is **generated**: the scripts write `mfn-page-items` directly
and re-running one **overwrites everything on that page**, including edits made in
BeBuilder. The run order and per-script description are in
[`build/README.md`](build/README.md).

The scripts find WordPress themselves (`build/bootstrap.php` walks up for `wp-load.php`,
or set `MIRAEX_WP_ROOT`), so they run on any machine:

```bash
php wp-content/themes/betheme-child/docs/build/build_home.php
```

Done by hand, and therefore **not** reproducible by re-running the scripts:

- the mega menu ↔ *Solutions* menu-item link (§4.6)
- anything the client later edits in BeBuilder

Decide with the receiving team which model they want going forward: keep editing through
the scripts (design stays consistent, edits in the UI get overwritten), or declare the
database authoritative from here and retire the builders. Mixing the two silently loses
work.

## 7. Caching and load

`build/configure_litespeed.php` holds the settings, with the reasoning inline. What matters
when this moves to a real host:

- **Page caching only works on LiteSpeed or OpenLiteSpeed.** On nginx the settings are
  stored and ignored. The intended host runs LiteSpeed; if that changes, swap the plugin
  for one that matches the server, because nothing else about the site depends on it.
- After deploying, confirm caching is actually on: a second request to `/` should come
  back with an `x-litespeed-cache: hit` header. Settings that are stored but inert look
  identical in the admin.
- **Nothing in the page is per-visitor** — no nonce, no personalised markup — so whole
  pages can be cached and served to everyone. Keep it that way; the moment something
  visitor-specific is printed into the HTML, full-page caching starts serving one
  visitor's page to another.
- Combining CSS/JS, deferring JS, critical CSS and unused-CSS removal are all **off on
  purpose**. BeTheme loads a dozen scripts that assume their own order, and those four
  settings are what break builder pages. Minify and lazy load are on and were verified:
  13/13 pages load, 22/22 images render, no JS errors, and the contact form's inline
  script survives HTML minification intact.
- `/wp-json/` is excluded from caching. The contact endpoint is POST and would not be
  cached anyway, but a GET endpoint added later would be.

**The load numbers that matter.** A first visit to the front page transfers roughly
3.2 MB — 39 KB of gzipped HTML, 355 KB of JavaScript and **2.8 MB of images**. Five
thousand of those at once is ~15 GB; behind a CDN, repeat visits cost only the HTML.
So a burst is a bandwidth problem, not a CPU one, and the fix is a CDN plus lighter
images (WebP/AVIF), not a bigger hosting plan. PHP workers only matter if page caching
is off — with it on, readers never reach PHP.

## 8. What the site tells visitors about itself

`betheme-child/inc/hardening.php` removes the version numbers and the discovery links
WordPress prints by default: the `generator` meta tag (which named the exact version),
the RSD/manifest/shortlink/oEmbed/REST link tags, and the `X-Powered-By` header naming
the PHP version. The REST API itself stays on — the contact form posts to it.

`readme.html` and `license.txt` were deleted; both are readable by anyone and name the
WordPress version. **A core update puts them back**, so delete them again after updating,
or block them at the server.

Two things are deliberately *not* done:

- **`wp-content` is not renamed.** Image URLs live inside PHP-serialized builder data, so
  a rename is the same length-prefix trap as a domain change (§3), and it fools nobody:
  cookie names, the login redirect and the markup still identify WordPress.
- **No "hide WordPress" plugin.** They add a rewrite layer over everything, break as often
  as they help, and a competent scan sees through them anyway.

Be clear about what this buys: it does **not** make the site unidentifiable. It removes the
version numbers, which is what turns a broad scan into a targeted one — a bot hunting for
"WordPress 7.0.4 with plugin X" moves on when the number is not offered. The security that
matters is elsewhere: keep WordPress, betheme and the plugins updated, and restrict
`/wp-login.php` and `/wp-admin/` at the server (IP allowlist or HTTP auth). Both are open
to the world today, and that is where brute-force traffic actually lands.

## 9. Missing / known gaps

- `/privacy/` and `/terms-of-service/` now exist, but they are **drafts awaiting legal
  review**. Every open decision is written into the page itself as `[TO CONFIRM: …]` —
  8 on the privacy page, 6 on the terms — so nothing can be missed. They must not go
  live to the public in this state: among other things they still lack the company
  registration number, the hosting provider, data retention periods, and confirmation
  of the HubSpot transfer mechanism.
- The WordPress **Site Title** had been set to the hero headline
  ("The quantum interconnect layer of the sovereign quantum era"), so it appeared in every
  `<title>`, the RSS feed and every WordPress email. `migrate_seo.php` sets it to *Miraex*
  with the tagline *Connecting Quantum*.
- Images are still JPEG/PNG at 2.8 MB per front-page load. Converting to WebP/AVIF is the
  single biggest performance win left; LiteSpeed can do it, but only through a QUIC.cloud
  account, which nobody has set up.
- `import_media.php` re-downloads images from the original static site
  (`ashy-forest-0b7587303.7.azurestaticapps.net`). Do not rely on it for a redeploy —
  transfer `uploads` instead; that host will not stay up forever.

## 10. Version control

The install is not under git today. Worth doing before handover — the child theme is the
only part that is hand-written:

```bash
cd wp-content/themes/betheme-child && git init && git add . && git commit -m "Miraex design layer + builders"
```

A `.gitignore` for the whole install is in the WordPress root if you prefer to track more
than the child theme.
